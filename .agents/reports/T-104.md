## Root cause
- `packages/db/src/repository/vault.repository.ts:15,55` — `findSecretById` and `deleteVaultSecretById` matched only on `id`; `packages/db/src/repository/deployed.workflow.repository.ts:57,69,80,97,118` — deployment lookups and mutations matched only on `workflowId`; and the controllers (`apps/api/src/controllers/vault.controllers.ts:52-72`, `apps/api/src/controllers/deploy.workflow.controller.ts:83-170`) never supplied the authenticated `req.user.id`, so any authenticated user could read, list or delete another user's secrets/deployments.

## Fix
- `packages/db/src/repository/vault.repository.ts:15-25` — `findSecretById(id, userId)` now uses `and(eq(id), eq(userId))`.
- `packages/db/src/repository/vault.repository.ts:55-65` — `deleteVaultSecretById(id, userId)` now uses `and(eq(id), eq(userId))` and `.returning({ id })` so the controller can detect a no-op deletion.
- `packages/db/src/repository/deployed.workflow.repository.ts:57-62,69-75,80-89,97-110,118-131` — `getDeploymentByWorkflowId`, `getALLDeploymentByWorkflowId`, `deleteDeploymentByWorkflowId`, `deactivateDeployment`, `activateDeployment` now require `userId` and combine it with the id predicate via `and(...)`.
- `apps/api/src/controllers/vault.controllers.ts:55-60` — `deleteSecret` passes `req.user.id` and returns 404 (`{ error: 'No Secret found' }`) when nothing was deleted; the success body `{ message: 'Secret deleted successfully' }` is unchanged.
- `apps/api/src/controllers/vault.controllers.ts:71-72` — `getDecryptedSecret` passes `req.user.id` to `findSecretById`; existing 404 and success shapes unchanged.
- `apps/api/src/controllers/deploy.workflow.controller.ts:94-95,99-105` — `getDeploymentController` scopes the lookup by `req.user.id` and returns 404 when no owned deployment exists; the owner success body is unchanged.
- `apps/api/src/controllers/deploy.workflow.controller.ts:135-140` — `getAllDeploymentController` scopes the lookup by `req.user.id` and **keeps the frozen `200 []` response** (`res.status(200).json(deployment ?? [])`) for a legitimate owner with zero deployments. An earlier 404 branch on an empty list was removed during this task as a contract regression; cross-user leakage is prevented by the userId-filtered query, not by the status code.
- `apps/api/src/controllers/deploy.workflow.controller.ts:157-159` — `deleteDeploymentController` passes `req.user.id`; the existing 404 and 200 response shapes are unchanged.

## Risks and limitations
- Frozen-list contract: cross-user deployment list reads now return `200 []` (empty, no leakage), not 404, by explicit instruction; callers cannot distinguish "not yours" from "none", but no data is disclosed.
- `getDeploymentController` returns 404 when the owner has no matching deployment (previously `200 null`); this was required to make cross-user single reads return 404.
- `activateDeployment` / `deactivateDeployment` signatures now require `userId`; there are no in-repo callers, so future callers must be updated.
- No live database integration test: repository scoping is proven by rendering the exact drizzle predicates, not by executing SQL against Postgres.
- Vitest's default failure reporter crashes on Node 20; passing runs are unaffected, but failing runs require the JSON reporter for full detail.
