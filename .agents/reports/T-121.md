## Root cause
- `apps/web/stores/workflow/transitions/runtime.ts:103` — `updateLogs` spread the stale `...state.logs` *after* the patched `[id]` entry, so the original record overwrote the newly patched record and every log update became a no-op.
- Assertion verdict: the assertion is correct and the behavior is wrong. The legacy source `apps/web/providers/WorkflowEditorProvider.tsx:275-278` contains the identical reversed spread; the pure transition copied that pre-existing bug. The provider is outside this lease and was not modified.

## Fix
- `apps/web/stores/workflow/transitions/runtime.ts:103` — changed `logs: { [id]: { ...existing, ...payload }, ...state.logs }` to `logs: { ...state.logs, [id]: { ...existing, ...payload } }`. The patch is now applied last, so it wins while all other records are preserved. This mirrors the already-correct `updateExecution` at `runtime.ts:73-76` and is the smallest change that fixes the contract violation.
- Lint remediation inside the lease: replaced all 21 `as any` test fixtures with explicit typed fixtures (`WorkflowNode`, `WorkflowExecution`, `WorkflowExecutionLog`, `WorkflowDefinition`) across six test files, and removed one unused import. No lint rules disabled, no suppressions added, no assertions weakened or deleted.
