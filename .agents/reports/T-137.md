## Proposal and approval
- proposal: Replace the global Vitest `@` alias with per-app Vitest `test.projects` so API and web suites resolve `@` according to their own tsconfig conventions, while preserving all existing includes/excludes/setup behavior and test coverage.
- trade-offs: (1) **Inline `test.projects` in root config (chosen)** — minimal, lease-compliant, no new files; keeps one authoritative Vitest config. (2) Separate `vitest.config.*` files per project — clearer ownership boundaries but requires additional files outside this lease and adds config sprawl. (3) Keep global alias and add per-test overrides — brittle and does not fix collection-time module resolution. No new dependency/tool was added.
- approval: Task T-137 assigned by coordinator with explicit lease `{ owner: foundation, paths: ["vitest.config.mts", ".agents/reports/T-137.md"], task: T-137 }` recorded in `.agents/ownership.yaml` and `.agents/ledger.yaml`.

## Changed
- `vitest.config.mts:1-44` — Replaced the global `resolve.alias["@"] -> ./apps/web` with three inline Vitest projects. `api`: `apps/api/**/*.{test,spec}.{ts,tsx}`, `environment: "node"`, `@ -> ./apps/api/src`, excludes web/packages/tests to prevent cross-collection. `web`: `apps/web/**/*.{test,spec}.{ts,tsx}`, `environment: "node"` default (DOM suites opt in via existing `// @vitest-environment happy-dom` pragma), `@ -> ./apps/web`, excludes api/packages/tests. `packages`: `tests/**/*` and `packages/**/*` test globs, `environment: "node"`, excludes apps to preserve the original broad/root+package coverage without alias collision. ## Risks and limitations
- **Residual Node/Vitest engine mismatch (known, not resolved by this task):** Vitest 5.1.1 requires Node 22.12+; the environment runs Node v20.19.5. When test suites fail, Vitest's reporter can hit `TypeError: Map.groupBy is not a function` on Node 20, obscuring the real failure output. With the alias collision fixed and `pnpm test` green (0 failures), that reporter path is not triggered. Upgrading Node to a Vitest-5-supported version (or pinning Vitest to a Node-20-compatible line, with approval) remains a separate follow-up.
- Project scoping is intentionally explicit (`include`/`exclude` per project) to avoid Vitest project-config inheritance surprises observed during `vitest list`. If new test locations are added outside `apps/api`, `apps/web`, `tests/`, or `packages/`, the config must be updated deliberately.
